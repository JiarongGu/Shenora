# surface-lexicon.txt — the words a PUBLIC TYPE NAME in Shenora is allowed to be built from.
#
# WHY THIS IS AN ALLOW-LIST AND NOT A BLOCKLIST OF BUSINESS WORDS.
# The owner's standing review criterion for this repo is "make sure this is a LIBRARY — we are not
# solving specific business logic; everything here has to be generic enough that any of our
# applications can adopt it". That is the single most important property the kit has, and until this
# gate it was the only invariant with no tripwire at all: `ApiSurfaceTests` detects that the surface
# CHANGED, never that a change was a good idea, and its documented workflow is to copy the `.actual`
# file over the baseline — so it waves domain vocabulary straight through.
#
# A blocklist ("Invoice", "Playlist", "Skin"…) cannot work here for two reasons. It is open-ended —
# it only ever catches the domain words someone already thought of, and the leak that matters is the
# one from the app nobody anticipated. And writing down the domain nouns of the private sibling apps
# would itself put what those apps DO into a public repo (`.claude/rules/sensitive-info.md`).
#
# Inverting it fixes both. Every word below is shell, platform, transport or hosting vocabulary. A
# new public type built only from these words cannot be domain-specific; a type that introduces an
# unknown word stops the build and a human decides which it is. When the answer is "this really is
# generic", add the word here — that edit is the review, and it is cheap next to the baseline update
# and CHANGELOG entry a new public type already needs.
#
# SCOPE: public TYPE names only. That is exactly what D22 governs ("every public type is named for
# its MECHANISM"), and it is the highest-signal, lowest-noise slice of the surface. Members are not
# swept — deliberately, so this gate keeps the property doc-drift was built on: precise checks that
# cannot cry wolf beat broad ones that get switched off.
#
# Derived 2026-08-01 from the 147 public types then shipping: 134 words, every one of them a
# mechanism. The kit passed its own criterion on the day the gate was written; the gate exists to
# keep it that way through the adoptions that have not happened yet.
#
# Format: one word per line, PascalCase segment as it appears in a type name. `#` starts a comment.
# A leading `I` on an interface is stripped before splitting, so `IClipboardService` needs only
# Clipboard + Service.

# `Segment` + `Run` + `Engine` (2026-08-06) — the segment-stream route, harvested from a consuming app that
# proved it on a device. All three name MECHANISM and none names a product:
#   · `Segment` is a piece of a stream produced on a fixed grid. Streaming-protocol vocabulary (HLS and DASH
#     both use it), not ours and not any app's.
#   · `Run` is one live production — started, writes numbered output, can be killed. Deliberately not `Job`
#     or `Task`: `Task` collides with the BCL, and `Job` is the app's word for work it schedules, which is
#     the noun the mission layer refused for the same reason.
#   · `Engine` names the SEAM an app plugs its own encoder into — `ISegmentEngine`. ⚠ This entry used to
#     say the kit "ships no implementation and never will (D42, D51)", which D52 corrected LATER THE SAME
#     DAY: the kit does ship a DEFAULT, assembled from a managed remux and the platform's own codecs. That
#     narrows D42 rather than reversing it — D42's objection was always VENDORING (megabytes every consumer
#     pays for, a licence every consumer inherits), and a default costing zero bytes and zero obligations
#     is neither. The word is still admissible for the better reason: it names a MECHANISM, and the seam
#     remains the escape hatch for reach the default lacks rather than the only door.
# ⚠ Watch `Engine` the way `Media` and `Download` are watched, and closer: the moment a type here DECIDES
# how to encode rather than asking the app, the kit has grown an engine, which D42 puts out of scope. A
# `SegmentEncoder`, `SegmentTranscoder`, or a codec ladder in `src/` would be that — argue those afresh
# rather than waving them past because this line exists.

# and the parallel is close enough to be worth stating: it is a published format name rather than a product
# concept, the type reads its header and does nothing else, and naming the format is the SMALLER commitment.
# `MediaContainerProbe` would over-claim — it reads Matroska and not MP4 — and the Archives lesson above is
# that a name which has to be explained by its contents is the wrong name.
# ⚠ The watch here is scope, not vocabulary: this may only ever READ a header. A `MatroskaWriter`,
# `MatroskaMuxer` or anything that produces one is a different argument (it is the translation layer's

Matroska
# `Mp4` + `Remuxer` (2026-08-07) — THE ARGUMENT THE LINE ABOVE ASKED FOR, made on its own terms.
# `Mp4Remuxer` reads Matroska and writes MP4. Note first what it is NOT: not a `MatroskaWriter`, which is
# what that warning was actually guarding against — nothing here produces a Matroska file, and the kit
# still owns exactly one direction.
#   · `Mp4` is a published container format name, admitted on precisely the terms `Zip` and `Matroska`
#     were: it names the format the type emits and nothing about a product. A `MediaRemuxer` or
#     `ContainerRewriter` would OVER-CLAIM in the way `MediaContainerProbe` would have — this reads one
#     container and writes one other, and the Archives lesson is that a name needing its contents
#     explained is the wrong name.
#   · `Remuxer` is the kit's OWN decided vocabulary already: `MediaPlaybackAction.Remux` has been the
#     planner's verdict since 2026-08-03. This type is the thing that performs the verdict the planner
#     already names, so the word is not new to the surface — only to the part of it this gate sweeps
#     (D22 is types; enum members are not swept).
# ⚠ And the scope test it has to keep passing (D52): a remux DECODES NOTHING. It copies frames and their
# decoder configuration verbatim into a different box — zero bytes shipped, zero licence weight, no codec
# written. The moment something here decodes or encodes a frame, the kit has grown the engine D42 puts out
# of scope, and `Mp4Transcoder` or a `Decoder` would be that — argue those afresh.
Mp4

# `Sample` + `Span` (2026-08-12) — in `Mp4SampleSpan`, one frame's place in the source and in the planned
# output, alongside `Mp4Layout` (`Layout` is already admitted for the activity vocabulary, further down).
#   · `Sample` is the ISO base media file format's OWN word for one frame of coded media — it is what the
#     boxes this type describes are called (`stsz` is the sample size table, `stss` the sync sample table).
#     Naming a thing what its format names it is the same argument that admitted `Mp4` and `Matroska`: it
#     is published vocabulary rather than a product concept, and `Mp4FrameSpan` would be the kit inventing
#     a private synonym for a word every reader of the spec already knows.
#   · `Span` is a RANGE — an offset and a length — which is as mechanical as a word gets.
#     ⚠ The obvious objection is `System.Span<T>`, and it is worth answering rather than waving past: this
#     is not a view over memory and does not pretend to be, which is why it is never bare `Span` but always
#     qualified by what it spans. `Range` would collide with `System.Range` far more confusingly (that one
#     really is two indices), and `Extent` or `Placement` name nothing the reader already has.
# ⚠ The watch here is the same one `Mp4` carries: these describe a COPY. The moment a type here describes
# a sample being decoded, resampled or re-encoded, the kit has grown the engine D42 puts out of scope.
# `Writer` (2026-08-07) — in `IMediaContainerWriter`, the MUXER seam. Admitted because it names a MECHANISM
# and nothing else: something that writes a container. The reasoning for wanting the seam at all is worth
# recording because it is not the obvious one — `MediaConversionOptions.Convert` already accepts a delegate,
# but that delegate is ALL-OR-NOTHING: a consumer wanting only their own AAC encoder, or only a native
# muxer, had to reimplement demux, timing, sample tables and interleave behind it. Cutting the pipeline into
# replaceable PARTS is the point (owner: "the issue is not the speed, its how to optimize this").
# ⚠ Watch it the way `Engine` is watched: a `Writer` that starts DECIDING what to encode has become an
# engine, which D42 puts out of scope. This one is TOLD what to carry and refuses what it cannot.
Writer
# `Reader` (2026-08-12) — in `Mp4LayoutReader`, the read half of what `Mp4Remuxer.Plan` already describes.
# Admitted on the identical grounds `Writer` was: it names a MECHANISM (something that reads bytes out of an
# existing description) and nothing about a product, and the base class library already uses the word the
# same way (`BinaryReader`, `StreamReader`). It decodes nothing and re-encodes nothing — it maps an
# already-planned byte range straight onto the source's own frames, one seek per span — so the same D42
# boundary `Writer` and `Mp4` both watch applies unchanged here.
# ⚠ Watch it the same way: the moment this type starts INTERPRETING a frame's content rather than its
# position, or deciding what belongs in a range rather than being told one, it has grown the engine D42 puts
# out of scope.
# `Computed` + `Remux` (2026-08-12) — in `ComputedRemuxExtensions`, the route that serves an MP4 over HTTP
# ranges WITHOUT ever writing one (D71). Both words describe the mechanism, and between them they are the
# only honest way to say what this route is: the OTHER delivery routes produce a file and then serve it.
#   · `Remux` is the kit's own decided vocabulary and already on the surface as `MediaPlaybackAction.Remux`,
#     the planner's verdict since 2026-08-03 — this is the same argument that admitted `Remuxer`, minus the
#     `-er`, because the type is not a remuxer: it DELIVERS what one would have produced. A bare
#     `Remuxer`-shaped name here would claim the type performs the copy, which `Mp4Remuxer` does.
#   · `Computed` names the distinguishing MECHANISM — the output is derived from the source's frame index
#     rather than produced and stored — and it is the word that makes the D71 split readable in one line:
#     the conversion route materialises, the segment route produces a frontier, this one computes. The
#     alternatives all say less: `Virtual` is a claim about existence rather than about how bytes arrive,
#     `Live` and `Dynamic` say only "not static", and `Lazy` describes a schedule, not a derivation.
# ⚠ The watch is exactly `Mp4`'s and `Reader`'s: this route DECODES NOTHING. It answers a byte range out of a
# layout somebody else planned. `Computed` beside a word like `Transcode`, `Encode` or `Effect` would be the
# kit growing the engine D42 puts out of scope, and `ComputedTranscodeExtensions` is not a name to wave past
# because half of it is already here.
Computed
Remux

# `Player` (2026-08-07) — in `IMediaPlayer`, and admitted only after arguing against the warning THIS FILE
# had already written about it (see the `Audio` note above, which named `AudioPlayer` as the shape that
# would mean the kit had grown a product). The gate fired on exactly the word it was built to catch, so the
# case has to be made rather than waved through.
#
# WHAT CHANGED IS THE PRODUCT DEFINITION, not the tolerance for domain words. D54 (owner, 2026-08-07):
# the kit is a hybrid app framework whose differentiator is native .NET capability, and its job is the
# translation layer for "what .NET can do and React cannot". A host-owned player is the clearest instance
# of that: iOS PAUSES a <video> the moment the app backgrounds, and AVPlayer does not. No amount of
# JavaScript closes that gap.
#
# WHY IT IS MECHANISM AND NOT DOMAIN, on the file's own tests:
#   · The `ProfileDirectory` test — do the platforms themselves use the word? AVPlayer (Apple), ExoPlayer
#     and MediaPlayer (Android), MediaPlayer (Windows). All three name this surface `Player`. It is
#     platform vocabulary in the same way `Audio` is.
#   · It names a MECHANISM: something that opens a source and advances a clock through it. Compare the
#     names it is NOT — `MediaLibrary`, `Playlist`, `NowPlayingQueue`, `AudioEffect` — every one of which
#     describes a PRODUCT built ON a player.
#
# ⚠ THE LINE, stated so the next contributor does not have to re-derive it. `IMediaPlayer` ships ONE
# source, open/play/pause/seek/close, and no queue, playlist, gapless, crossfade, shuffle or effects —
# the same refusal that keeps a queue model out of IPlaybackSession, for the same reason: only the app
# knows what "next" means. **A `Next()` on this interface is the tell that it has become a product.**
Player

# `Video` (2026-08-12) — in `AndroidMediaVideoConversion`, the platform half that decodes a picture the
# webview refuses. It names a STREAM KIND the platform itself names: `MediaStreamKind.Video` has existed
# since the planner shipped, so the word was load-bearing everywhere except a type name.
#
# ⚠ ADDED, REMOVED AND RE-ADDED THE SAME DAY, which is the gate working rather than churn. It went in for a
# parallel video tier; unification deleted every type carrying it, and `Lexicon_has_no_unused_words` made me
# take it out ("an allow-list that only grows reviews nothing"); the Android converter brought it back. Each
# move was forced by a check, not by taste.
#
# WHAT EARNED IT is a measurement. On API 36 / WebView 133 the device decodes `mpeg4` to a real 480x270
# frame while `canPlayType` answers "" for it — and the page then reaches readyState=4 with NO error and a
# 0x0 picture. Sound over a blank rectangle, silently. That is D59's gap with the picture in it.
#
# ⚠ THE LINE, in the shape the `Player` note uses: this converts ONE stream using codecs the OS already has.
# The names it is NOT: `VideoEditor`, `VideoFilter`, `VideoEffect`, `Thumbnailer`, `VideoLibrary`. **A crop,
# a scale-for-quality or an overlay is the tell that the kit has grown an editor** (D51: no engine, ever).
Video

# `Background` + `Transfer` (2026-08-12) — in `BackgroundPlaybackTransfer`, which moves a playhead between
# the page's player and the platform's when the app leaves the foreground.
#
# `Background` names an app LIFECYCLE STATE the platforms name themselves (`didEnterBackground`, `onStop`,
# `UIBackgroundModes`) — hosting vocabulary, exactly like `Headless`. It is not a scenario word: it does not
# describe what an app is FOR, it describes where the process is.
#
# `Transfer` names the MECHANISM: one responsibility moving between two implementations of one contract.
#
# 🔴 IT WAS `Handoff` FIRST, and the gate is what made me look at it. Apple ships a branded feature called
# Handoff — device-to-device continuity — and this kit ships an iOS shell, so an adopter meeting
# `BackgroundPlaybackHandoff` there would reasonably expect Continuity. A public type name that collides
# with a platform feature ON A PLATFORM WE SUPPORT is the naming mistake this file exists to catch.
#
# ⚠ THE LINE: this moves a POSITION between two players and nothing else. The names it is NOT:
# `BackgroundService`, `BackgroundTask`, `BackgroundQueue` — a general background-work API is a different
# thing entirely, and the kit does not have one.
Background
Transfer

# `Access` (2026-08-12, D71) — in `MediaAccessOptions`, the containment boundary `MediaConversionOptions`,
# `SegmentStreamOptions` and `MediaPlayerOptions` used to each declare on their own (`AllowedRoots` +
# `CacheRoot`), stated once instead.
#
# THE `ProfileDirectory` TEST: platforms already use this exact word for this exact thing — Android's
# runtime permissions are literally named `READ_MEDIA_*` / storage "access", iOS frames the same idea as
# sandbox/file-access entitlements, and the BCL's own `FileAccess` enum predates all of them. It is not this
# kit's invention; it is the word every platform already reaches for when the question is "may this code
# touch that path".
#
# THE "would a second app disagree" TEST: no — every consumer of a delivery route needs the same three
# answers (where may it read, where does it cache, which module does it speak on), and none of those is a
# choice specific to media, or to any one app's domain. That is exactly why D71 pulled it out from three
# separate declarations into one.
#
# ⚠ THE LINE, in the shape the other watched words use: this type decides CONTAINMENT and CACHE LOCATION
# and nothing else. The names it is NOT: `MediaPermissions`, `MediaSecurity`, `MediaPolicy` (already taken,
# and for a different question — WHICH CODECS play, not WHERE FILES live) — a type that started asking an
# app to describe a permission MODEL rather than a boundary would be the kit growing an authorization
# product, which is out of scope.
Access

# ── System transport / Now Playing (Shenora.Core, 2026-08-04) ─────────────────────────────────────
# `IPlaybackSession` and friends publish to the OS's media transport surface (lock screen, media
# notification, SystemMediaTransportControls) and receive its commands back. Every word was already here
# for other reasons — Playback, Session, Progress, Info, State, Command, Request — which is itself the
# evidence that the naming stayed on mechanism vocabulary. Only the PLURAL is new: `PlaybackCommands` is
# the flags SET of controls the OS should offer, distinct from the single `PlaybackCommand` it sends back.
#
# ⚠ Note what is deliberately NOT here: Artist, Album, Track, Artwork. The record's fields are Title /
# Subtitle / GroupName precisely so this contract can sit in Shenora.Core — which every package
# references — without putting music vocabulary on the surface of an app that has none. Fields are not
# swept by this gate, so that discipline is a review matter; it is written down here so the next person
# renaming them for convenience meets the reason first.
Commands

# ── Live status surfaces (Shenora.Core + Shenora.iOS, 2026-08-04) ─────────────────────────────────
# `ILiveActivities` / `LiveActivityState` put a long-running job on the OS-rendered strip an app gets
# while backgrounded — iOS's Dynamic Island and lock screen today. `Live` and `Activity` are both
# mechanism words: a live surface is one the OS keeps updating, and an activity is a unit of work in
# progress. Neither names a product concept, and the state record carries Title / Subtitle / Progress
# with no domain vocabulary at all.

# ⚠ `Activity` is the word to watch here, for the same reason `Media` and `Download` are watched above:

Live

# `Appearance` (2026-08-09, D69) — the static half of a live surface: which SF Symbol and which tint the
# kit's generic widget renders. Admitted rather than renamed because it names a MECHANISM the platform
# itself has: ActivityKit splits an activity into fixed attributes and changing content, and this is the
# fixed half. It is also what makes the widget GENERIC — the alternative to a config the widget reads is
# an app writing SwiftUI, which is the Swift dependency D69 exists to remove.
# ⚠ Watch it the way `Activity` is watched. It stays legitimate while it describes HOW a kit-drawn
# surface is rendered; the moment it starts carrying an app's design system it has become the thing D13
# says the kit does not ship, and a `Theme`/`Style` sibling appearing beside it is the tell.
Appearance
# ── The Live Activity LAYOUT vocabulary (2026-08-09, D69) ────────────────────────────────────────────
# Six words admitted together, for a tree an app describes in C# and the kit's generic widget interprets
# at runtime — so an app gets a styled Live Activity with no Swift.
#
# 🔴 THE ARGUMENT, because this is the closest the kit has come to shipping a design system and D13 says
# it must not. What makes these MECHANISM words rather than presentation ones is that the element set is
# CLOSED AND TINY, and it is tiny because the SURFACE is: a Live Activity is a lock-screen card and four
# regions measured in millimetres. Text, a symbol, a bar, and a way to put them beside or under each
# other is the whole of what fits. That describes a PLATFORM SURFACE; it is not a way to express an
# app's design.
#
# ⚠ THE TELL THAT IT HAS GONE WRONG, and it is specific: a request for nesting depth, absolute
# positioning, images, custom fonts, or a word like `Style`/`Theme`/`Padding`/`Font` arriving beside
# these. Every one is the moment to answer "write the four SwiftUI view bodies"
# (`ShenoraLiveActivityViews`, which stays first-class) rather than to widen this list. `Role` is here
# INSTEAD of `Style` deliberately: it names what a line IS — headline, caption, value — which the widget
# maps onto the platform's own type scale. Semantic in, visual out.

# ── File dialogs, split per method (2026-08-05) ────────────────────────────────────────────────
# `Open` and `Save` are the only VERBS in this file, and they were admitted deliberately rather than
# renamed around. Three things decided it:
#   1. They are the PLATFORM's own vocabulary, not ours — `OpenFileDialog` and `SaveFileDialog` are
#      BCL type names, and every shell expresses the same pair (ACTION_CREATE_DOCUMENT,
#      UIDocumentPickerViewController's export mode).
#   2. `IFileDialogs` has used them as METHOD names since P5.5. Members are not swept by this gate,
#      which is the only reason this never fired before — so the words were already the kit's, and
#      what changed is that the split PROMOTED them to type names.
#   3. Every mechanism-noun alternative was worse. `FileSourceOptions`/`FileTargetOptions` are
#      buildable from words already here, and they mis-describe the folder case: a folder pick is a
#      SOURCE when it grants a working directory and a TARGET when it chooses an export destination,
#      so the honest name for that one is neither.

# naming ACTIONS rather than mechanisms (D22). These two are anchored to a specific OS dialog that
# every platform ships; a `LoadOptions`, `ImportOptions` or `ExportOptions` would not be, and must be
# argued on its own merits rather than waved past because this section exists.

# `Remote` (2026-08-19) — for `RemoteMediaSource`, the source a `MediaSourceRegistry` issues a handle for.
